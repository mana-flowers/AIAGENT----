# 创游助手 · 答辩演示脚本

> 用途：模块 B「原型演示视频（≤5分钟）」录制脚本 + 模块 C「现场展示答辩」串讲词。
> 演示载体：`demo.html`（双击即开，零依赖）为主；`main.py`（API 内核）为辅，用于展示真实后端能力。

---

## 一、演示前置检查（开始前 2 分钟）

- [ ] Chrome / Edge 打开 `demo.html`，等待启动动画结束（约 1.5 秒）
- [ ] 浏览器全屏（F11），确认三栏布局完整、游戏画面在动
- [ ] 键盘试一下 `← → ↑ J`，确认角色能移动、跳跃、攻击
- [ ] 准备一个空输入框，录屏软件开始录制

---

## 二、5 分钟演示流程（逐幕脚本）

### 【第 0 幕 · 开场定位】0:00–0:25

**操作**：展示初始界面，鼠标缓慢划过三栏。

**讲词**：
> "各位评委老师好，我是××队，今天演示的项目是**创游助手**——一个用 Python 脚本操控 Godot 4 引擎、能听懂玩家意见并自动改写游戏的智能体。它不是聊天机器人，而是真正能改代码、画素材、配音效、并且**记住每一条要求、随时回滚**的开发伙伴。左边是玩家意见入口，中间是五个智能体的协作流水线，右边是当前正在运行的游戏《史莱姆勇者》——画面里的角色、史莱姆、音效、动作，全部由程序现场生成，没有用到任何外部美术素材。"

**要点**：第一句话就点出"操控 Godot 4 + 程序化创作 + 记忆回滚"三大差异点。

---

### 【第 1 幕 · 首次生成】0:25–1:10

**操作**：点击一键需求 ①「帮我做一个史莱姆勇者横版闯关游戏」，点「开始创作」。

**画面**：四个智能体依次点亮 → 日志打字机滚动 → 游戏更新。

**讲词**：
> "我先让它从零做一个游戏。看中间——**规划师**先把这句话拆成脚本、素材、音效、自检四类任务；接着**代码师**调用工具改写 GDScript，日志里能看到它注入了重力、跳跃力这些参数；然后**美术师**程序化重绘像素角色和史莱姆，并用 Web Audio 合成 8-bit 音效；最后**质检师**自动跑一遍自检。整个过程是可观测、可追溯的——每一条日志都是真实执行记录。"

**要点**：让评委看到"感知—规划—工具—执行"的完整链路，对应评分表技术架构得分点。

---

### 【第 2 幕 · 玩家意见驱动修改】1:10–2:00

**操作**：点击需求 ②「把主角改成粉色，史莱姆速度调快」，点「开始创作」。

**画面**：日志显示意图解析"2 项变更"→ 游戏里主角变粉色、史莱姆变快；左侧需求账本新增一条。

**讲词**：
> "现在模拟玩家提意见：'把主角改成粉色，史莱姆速度调快'。注意看——我没有改一行代码，智能体自己完成了意图解析，识别出两项变更，代码师和美术师协同改了配置和素材。游戏里的主角**当场变成粉色**，史莱姆移动明显加快。同时左下角**需求账本**自动记下了这条意见——这是它和普通 AI 编程助手的第一个本质区别：**所有要求都会被永久记住**。"

**要点**：这是最直观的"惊艳点"，鼠标指向变色处，停顿 2 秒让评委看清。

---

### 【第 3 幕 · 自检自查闭环】2:00–2:35

**操作**：指向右侧「自检自查报告」面板（健康分、自动修复数、6+3 项检查）。

**讲词**：
> "每一次生成后，质检师都会自动执行 6 条静态规则加 3 个运行探针。这里有个真实场景：刚才史莱姆速度被调到 1.8，超过了安全阈值，自检**自动把它钳制到 1.5**——报告里能看到这条'自动修复'记录。也就是说，玩家提出的夸张要求不会直接把游戏改坏，系统会自查并纠偏，形成一个'生成—检测—修复—复检'的闭环。"

**要点**：对应评分表"自检自查""量化评测"得分点。

---

### 【第 4 幕 · 记忆调用】2:35–3:10

**操作**：在输入框输入"我之前提过哪些要求？"，点开始。

**画面**：日志显示"检测到记忆检索意图 → 检索需求账本 → 命中 N 条历史要求"，逐条列出之前的意见。

**讲词**：
> "第二个本质区别是**随时调用**。我来问一句'我之前提过哪些要求'——看，智能体从需求账本里把前面所有意见原样检索了出来，每条都带时间和编号，可以引用溯源。这意味着多轮对话中它不会'失忆'，任何一条历史要求都能被重新调取并纳入本次生成。"

**要点**：对应评分表"多轮记忆指代消解""知识库检索与引用溯源"得分点。

---

### 【第 5 幕 · 随时回滚（高潮）】3:10–4:00

**操作**：点击版本时间轴里 `v1 · 初始版本` 的「↩ 回滚到此版本」。

**画面**：游戏主角从粉色**变回初始蓝色**，日志显示"回滚指令 → 校验快照哈希 → PASS → 恢复完成"。

**讲词**：
> "最关键的第三个区别：**随时回滚**。每次修改都会生成一份内容寻址快照，写进不可篡改的事务链。现在我一键回滚到最初版本——游戏**当场变回蓝色主角**，而需求账本的内容一条没丢。这就是我实现的'需求账本 + 事务链 + 内容寻址快照'三件套：改得回去、查得到源头、记不住的东西不存在。"

**要点**：这是全场最高潮，回滚后画面变化要停在屏幕上 3 秒。对应"可回滚""可追溯"得分点。

---

### 【第 6 幕 · Godot 真实产物（可选加分）】4:00–4:35

**操作**：切到文件管理器，打开 `godot_project/` 目录，展示 `project.godot`、`scripts/*.gd`、`assets/*.wav`。

**讲词**：
> "演示界面背后是真的在生成 Godot 4 工程。这是刚才生成的产物：有项目配置、GDScript 脚本、场景文件，还有程序化生成的 SVG 美术和 WAV 音效——全部由代码产出，可以直接拖进 Godot 4 打开运行。"

**要点**：如果现场有 Godot，可打开展示真实运行，效果翻倍。

---

### 【结尾 · 价值总结】4:35–5:00

**讲词**：
> "总结一下，创游助手解决的不是'能不能生成游戏'，而是'生成之后能不能被玩家持续地、可控地修改'。它把玩家的自然语言意见，变成可追溯、可自检、可回滚的真实工程变更。这就是我对'AI 赋能游戏开发'的理解。谢谢各位评委老师，欢迎提问。"

## 三、答辩问答预案（高频问题）

| 评委可能提问 | 建议回答要点 |
|---|---|
| 和 Cursor / Copilot 这类 AI 编程助手有什么本质区别？ | 它们是一次性代码补全，我们是**面向玩家意见的持续演进闭环**：需求账本全留存、自检自动纠偏、快照可回滚、 Godot 工程真实生成。核心差异是"改得回去、查得到源头"。 |
| 为什么选多智能体而不是单智能体？ | 游戏开发天然异构：代码、美术、音效、质检是不同工具链。主从式架构让每个 Worker 专注一类工具，Master 负责编排和一致性，避免单体 Agent 上下文污染；也便于可观测日志按角色追溯。 |
| 记忆是怎么实现的？会不会无限膨胀？ | 需求账本 append-only 存 JSON，检索走关键词 + 标签；生成时把全部需求打包成上下文。膨胀问题通过"近期优先 + 快照压缩"缓解，方案书 5 章有量化指标说明。 |
| 回滚是怎么保证一致的？ | 每次变更写入哈希链事务，快照以配置内容寻址（SHA-256 截断）。回滚即恢复该快照的完整配置并重新生成 Godot 工程，哈希校验保证不被篡改。 |
| 演示用的是真实大模型吗？ | 当前版本采用**可配置 LLM 网关**：默认 mock 模式保证答辩稳定，接口层已预留，填入 API Key 即可切换真实模型。这既是稳定性设计，也是工程化考量。 |
| 指标是怎么测的？ | 方案书 5.4 节定义了 6 项量化指标（意图识别准确率、生成成功率、自检命中率、回滚一致性、P95 延迟、需求召回率），每项都写了测量方法和 24 个评测任务卡，不是设想而是可复现实验。 |
| 合规与原创性怎么保证？ | 全部美术/音效/脚本程序化生成，无第三方素材；不提交真实密钥；仓库附原创性与数据合规承诺书。 |
